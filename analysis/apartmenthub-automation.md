# ApartmentHub automation reference analysis

Reviewed 14 October 2026. Reference: `C:/Users/paule/Downloads/apartmenthub/apartmenthub`, latest local commit `830a1050` (13 October 2026). This is a source review, not confirmation of the deployed application. No sender, development server, script, test suite, live database, or external messaging endpoint was run. No credentials or customer records were copied.

## Recommendation

Reuse the workflow decisions, reminder guards, message previews, activity history, and delivery reporting concepts in AgencyDesk. Build them against AgencyDesk's existing single-agency contacts, companies, leads, versioned proposals, projects, milestones, follow-up tasks, and authentication. Introduce a provider-neutral delivery interface using the user's own credentials. Do not transplant ApartmentHub's sending app, Zoko account, Gmail delegation, hardcoded recipients, n8n workflows, Salesforce mirrors, locale routes, or i18n modules. Audience broadcasts are an optional later extension because campaigns are excluded from AgencyDesk version one.

Most automation is ordinary deterministic business logic. AI is not necessary to decide whether a reminder is due, suppress a recipient, claim a job, or send an approved message. Hermes is a separate integration contract in this repository, not an API key interchangeable with Zoko.

## Broadcasting, suppression, and delivery

The broadcast create route uses the `apartments` permission, not unauthenticated client credentials. Server-side secrets stay out of the browser. `crmBroadcast.js:78` reads all suppression pages, avoiding a default REST page-size cutoff. `suppressed_phones()` in `current_schema.sql:3874` unions manual suppression with case-insensitive Zoko tags for opt-out, marketing opt-out, invalid numbers, and archived contacts.

The create route stops if suppression cannot be read (`:163`), stops if tag-coverage lookup fails (`:185`), and requires 99% checked tag coverage (`:33`, `:199`). However, 99% is not the same as checking each intended recipient: up to 1% can have unknown status. Test-phone sends bypass the normal segment suppression branch. Its terms filter also deliberately becomes disabled if an expected backfill/column is absent (`:244`). AgencyDesk should require affirmative eligibility for every marketing recipient and recheck consent at dispatch, not only when creating a potentially long-running job.

The process route claims at most 150 recipients by updating only still-pending rows and returning the rows actually won (`src/app/api/admin/crm/broadcast/[jobId]/process/route.js:138-169`). It paces provider calls at 300 milliseconds (`src/services/crmBroadcast.js:15`), writes each outcome, stores the provider message ID where supported, and atomically updates aggregate counters with a recount fallback (`process/route.js:185-237`). Database uniqueness on `(job_id, phone)` prevents audience overlap inside one job (`current_schema.sql:8667`). API failures become terminal failed recipient rows; there is no general exponential retry of those failed rows here.

The webhook validates a server-held URL secret using constant-time comparison (`src/app/api/webhooks/zoko/[secret]/route.js:55`). Inbound replies have deterministic message keys and a unique database constraint (`src/lib/zoko/inboundReply.js:64`; `current_schema.sql:8629`). Delivery receipts correlate by provider message ID, falling back to the newest message for the phone when the receipt has no ID (`webhook route:109-116`). A read receipt implies delivery (`:133`). The parser only accepts delivered/read statuses; failed delivery events are not reconciled by this parser (`src/lib/zoko/deliveryUpdate.js:50-53`). Most non-insert receipt failures still return 200 and can be lost rather than retried. This is useful analytics scaffolding, not a complete delivery ledger.

## Reminder decisions worth carrying over

The viewing schedule composes booking date plus local time in `Europe/Amsterdam`, handles a viewing crossing midnight, and cancels pending rows for the old slot when rescheduled (`current_schema.sql:3438-3482`). It prefers the actual apartment FK and only falls back to event URL matching when exactly one apartment matches (`:3491-3515`). The snapshot schedules two pre-viewing reminders and four after-viewing steps: 24 hours and 2 hours before, then 15 minutes, 4 hours, 17 hours, and 40 hours after (`:3523-3628`). The later `20261006190000_drop_24hr_before_viewing_reminder.sql` retires the 24-hour pre-viewing step to avoid duplicating the booking confirmation. Treat that as an intended delta, not proven deployed behavior.

The due-row processor locks rows with `FOR UPDATE SKIP LOCKED` (`current_schema.sql:2902`). It checks cancellation (`:2904`), active apartment status (`:2951`), documents complete for document-chasing steps (`:2966`), and offer already made for post-viewing steps (`:2996`). `doc_chase_suppression_reason()` compares both viewing and document ladders: the same step across a different ladder is suppressed for seven days, any document chase across a different ladder for eleven hours; steps in the same ladder stay exempt (`:1039`, `:1133`). The route independently checks cancellation/docs/listing before delivery (`send-viewing-reminder/route.js:158-207`). These are good examples of rules that should be dependency-free functions with explainable skipped reasons in AgencyDesk.

Invoice guards distinguish first-invoice generation, actual send, deferral, possible payment, and finance review. `shouldSkipInvoiceReminder.js:103-116` prevents reminders for unsent/undelivered invoices, returns, collection, cancellation deals, and medium/high-confidence possible payments. Low-confidence matches require a draft with internal warning instead of sending that warning to the client (`invoiceReminderStep.js:283`; `invoiceSending.js:516`). Human bank confirmation remains separate from reminder delivery.

## Current source versus historical infrastructure

`AGENTS.md` and `CLAUDE.md` say n8n was switched off on 30 September and Salesforce is deprecated. They explicitly forbid agent database writes and pushes. The provided production schema dump nevertheless still contains n8n HTTP trigger bodies and document-reminder sending functions. The migration directory holds pending deltas which have not been folded into the dump. Source files, old comments, API reference docs, and delta migrations disagree in places; none substitutes for verified deployment state.

- `20260928120000_drop_dead_webhooks.sql` and `20260930170000_switch_off_n8n.sql` remove old notification triggers while preserving CRM bookkeeping in mixed functions. The latter unschedules the document-reminder worker (`:264-285`). New document reminder rows can still be scheduled but never delivered until a replacement is implemented.
- `supabase/schema/current_operational.sql:11-14` explicitly labels the job list reconstructed and not checked against the live database. It describes broadcast every minute, viewing every five minutes, and tag/segment sync every fifteen minutes, with invoice reminders daily at 08:00 UTC (`:58`, `:71`, `:100`, `:133`, `:154`). These are repository-intended schedules, not verified current jobs.
- LOI email queue columns and partner tables are absent from `current_schema.sql`; their routes depend on delta migrations. Do not present these modules as already fully operational.
- `20261008190000_partner_daily_cron.sql` proposes daily processing at 05:00 UTC, digest at 17:00 UTC, and Friday nudges at 15:00 UTC. Comments describe Amsterdam times, but fixed UTC clocks shift local behavior with daylight savings. AgencyDesk should store an explicit configured business timezone and UTC due instants.
- API documentation saying every invoice reminder is only drafted is stale. Current sender attempts actual delivery and drafts only on review/failure. Likewise the older Cal.com docs say the HMAC is optional; current route rejects missing/invalid signatures (`calcom/route.js:343-361`). Prefer current executable code for these details.

## Hermes specifically

`src/services/willemHook.js` is a buyer-lead alert hook to a separate Hermes gateway. It builds a particular internal recipient message and signs the JSON body with a server-held `WILLEM_HOOK_SECRET` (`:39-53`). Defaults are a five-second timeout and one retry for network errors, 408/429, and selected 5xx responses (`:32`, `:111-125`). Missing configuration is recorded as `no_hook`, not success. A 2xx result means the gateway accepted the request, not that WhatsApp delivery was verified.

The file explicitly states that header convention, JSON casing, acknowledgment schema, retry/idempotency behavior, and response-code contract are not yet defined (`:15-21`). `/api/hermes/buyer-leads` offers a protected catch-up feed using an HMAC-derived bearer token and a timestamp cursor (`route.ts:9-47`; `src/lib/hermes/buyerLeadsFeed.ts:15`). The consumer is expected to deduplicate by lead ID. Timestamp-only inclusive pagination can fail to advance if a full page shares one timestamp; AgencyDesk should use a `(created_at, id)` cursor.

Do not copy the existing hook destination, recipient, key, or WhatsApp Web dependency. AgencyDesk's Hermes adapter needs the user's actual Hermes endpoint and documented acknowledgment/idempotency contract. A WhatsApp adapter likewise needs its own sender identity and template mappings; changing an API key alone does not replace account-specific template IDs or approved variables.

## Reliability issues to fix in a new implementation

These are source-level risks, not observed live incidents:

1. **Viewing sends are marked successful before delivery.** SQL sets `sent_at` immediately after asynchronous `net.http_post` (`current_schema.sql:3095-3109`). A 422, 502, timeout, route-side skip, or later provider failure does not undo it. The route itself acknowledges this (`send-viewing-reminder/route.js:25`). Use queued/processing/accepted/delivered as distinct states and record provider acknowledgment after sending.
2. **Broadcast recovery uses row creation age instead of claim age.** Worker resets every `sending` row whose `created_at` is over ten minutes old (`current_schema.sql:2573-2580`). An old queued recipient just claimed by a live chunk already meets that cutoff. Concurrent ticks can therefore requeue active work and duplicate messages. Use lease expiry and owner tokens, not `created_at`.
3. **Crash after acceptance can duplicate any provider send.** Broadcast results are saved after the provider returns. Without provider idempotency or an uncertain-result reconciliation phase, a crash between send and write can resend. Database uniqueness alone does not make an external side effect exactly once.
4. **Cancellation is only checked at chunk entry.** Broadcast process reads cancelled state before claiming (`process/route.js:134`) but does not recheck it before each later recipient. A cancelled running chunk can continue. Consent/suppression is also frozen at create time rather than rechecked during processing.
5. **LOI claim is not atomic ownership.** Its retry sweep updates a dossier by ID only, without comparing prior due/sent state or returning a won lease (`loi-email-retry/route.js:70-89`). Overlapping sweeps or the immediate attempt can race. Backoff is 10, 30, 120, 360, 1440 minutes, capped to six attempts by default, so comments describing guaranteed delivery overstate it.
6. **Invoice reminder failure has no automatic queue retry.** The SQL first inserts a unique reminder row, then dispatches. Later daily scans only select rows without an existing reminder (`current_schema.sql:2807`, `:2821`). Failed or lost route calls therefore require manual intervention. A send accepted but not recorded also risks duplicate manual retry (`invoiceSending.js:549-552`).
7. **Bank check failure can still allow a chase.** `liveBankMatchFor` returns null when config is missing or when the check throws (`invoiceReminderStep.js:174`, `:201-202`); the downstream sender treats only an actual low-confidence match as review-required. Its log says drafting without the check, but executable flow can auto-send. Make bank-check unavailable an explicit review state.
8. **Partner outbox is an incomplete queue.** `deliverById` does no conditional claim/status guard (`deliver.ts:111-120`). Daily retries only select queued/failed messages (`:125-130`), so partly-sent rows never retry missing channels; naive manual redelivery resends already successful channels. Track one delivery record per message/channel, claim each separately, and retry only failures. Forced account notices ignore all channel toggles (`src/lib/partner/messages.ts:42-50`), so keep essential transactional settings separate from marketing opt-out.
9. **Operational logs contain contact/message payloads.** Broadcast send helper logs recipient and all arguments (`crmBroadcast.js:261`); Cal.com logs raw body preview and headers (`calcom/route.js:337-339`). The new application should log IDs, states, latency, and redacted errors instead.

## AgencyDesk implementation blueprint

AgencyDesk's actual foundation is inquiry -> lead -> published proposal revision -> atomic acceptance -> project and milestones (`src/lib/domain.ts`; `README.md:3`, `:29-33`). Its current follow-up model is `follow_up_tasks`; internal staff use `staff_members` and clients use live `client_memberships`. Version one explicitly excludes multiple agency workspaces, campaigns, invoicing, payments, uploads, and AI. There are no current appointment, invoice, or separate deal entities to integrate. Do not add multi-tenancy or replace existing authorization to implement initial notifications.

Use this sequence: confirmed CRM event -> pure rule evaluation -> frozen message preview -> approval or configured automatic rule -> transactional outbox -> leased worker -> provider adapter -> authenticated webhook/inbox event -> activity timeline. `docs/content-and-automation.md` already recommends a transactional business-event outbox and unique event IDs. Build on that design while preserving the existing proposal acceptance transaction and idempotent project handoff. Keep Directus content publication separate from CRM business events.

Suggested new automation records for the existing single agency:

- `automation_rules`: event, conditions, delay, channel, template version, approval mode, enabled state. No workspace column is required for this scope.
- `automation_events`: subject ID/type, company/lead/contact reference as appropriate, event key/version, occurred time, small context payload; unique event identity.
- `message_jobs`: event/rule, existing contact/lead/company relationship, recipient/channel, stable dedup key, due time, approval status/actor, rendered snapshot, provider connection reference, queued/processing/accepted/delivered/read/failed/skipped/cancelled state. Capture the recipient used for this send without inventing a new contact ownership model.
- `message_attempts`: job, attempt number, lease owner/expiry, started/finished time, provider message ID, retry classification, sanitized failure details.
- `contact_channel_preferences`: existing contact or lead/channel relationship, consent, suppression reason and source, last-change timestamp. Current contact/lead types have email but no phone field, so WhatsApp needs a separately validated phone field and opt-in before enabling delivery.
- `provider_events`: provider connection/event ID with a unique inbox key, authenticated raw-event retention policy, received time and correlated job. Store uncertain outcomes for reconciliation.

Preserve live `staff_members` and `client_memberships` checks: automation configuration, approval, history, and manual retry belong behind existing staff permissions; client-readable records must retain existing company isolation. Determine recipients from existing relationships and current membership rules where access-sensitive messages are involved. Never trust client-submitted company/contact IDs or stale JWT metadata to grant access. A worker must use a narrowly scoped privileged path without expanding Next.js's current no-service-role-key deployment model.

The server-only provider interface should expose `sendTemplate` / `sendEmail`, a stable idempotency key, typed accepted/rejected/unknown outcomes, and webhook parsing. Implement only the provider the user selects first; preserve the interface for WhatsApp or Hermes later. A dry-run adapter should render and record intended sends without touching an external service. Credentials should be referenced from encrypted server storage or environment configuration for the single agency, never supplied in frontend requests or copied from ApartmentHub. Adding workspace-scoped connections would be an optional future product expansion, not a prerequisite.

Keep one English UI and one set of templates. Provider template-language metadata may still be required by the selected messaging API; that is not a reason to import i18n routing or translation modules.

Initial rules should use existing domain events: inquiry received -> acknowledgment; proposal revision published -> client notification and configurable follow-up; proposal accepted -> project handoff notification; follow-up task due -> staff reminder; milestone approaching/completed -> appropriate staff/client update; project update created -> notification to authorized company clients. Proposal declined, superseded, accepted, or lead archived should invalidate any now-inappropriate proposal follow-up. Use the accepted immutable revision for scope and price context, not the latest draft. Respect Asia/Manila scheduling inputs and stored `timestamptz` values already used by AgencyDesk.

Start with previews and visible pending jobs, then enable automatic delivery per rule using the user's own provider connection. Appointments with confirmations/rescheduling, document collection ladders, invoice payment reminders, broad campaigns, and multiple agency workspaces are optional future product decisions requiring new domain models; they are not required to reuse ApartmentHub's automation engineering.

Verification for a future implementation should cover concurrent claim ownership, superseded/accepted proposal follow-up invalidation, recipient preference changes while queued, company isolation and membership revocation, crash after provider acceptance, timeout versus explicit rejection, duplicate/out-of-order callbacks, partial multichannel delivery, and retry exhaustion using fake providers. Appointment rescheduling and campaign opt-out tests become relevant only if those optional modules are added. Deployment validation requires confirming applied migrations, job schedules, provider sender identity, template approvals, and the chosen Hermes contract, without contacting reference-system customers.
